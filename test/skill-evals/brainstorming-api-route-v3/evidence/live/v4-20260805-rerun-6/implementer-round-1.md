根据已确认约束，三种方向比较如下。

### 方案一：同步批量入口

新增批量公共接口，例如：

```text
collect(ids: string[]) -> BatchResult[]
```

其中 `ids.length` 必须为 1–100，结果与输入逐项对应，保留输入顺序和重复 ID。每项明确表达成功、缺失或失败，例如：

```js
[
  { id: "doc-1", status: "ok", document: {...}, error: null },
  { id: "missing", status: "not_found", document: null, error: null },
  { id: "doc-3", status: "failed", document: null, error: { code: "..." } }
]
```

这样成功项不会因单项失败而丢失，调用方可以仅按失败项重试。请求级错误只用于参数非法、超过上限或整个服务不可用等无法形成逐项结果的情况。

兼容性上，保留现有 `getDocument(id)` 和 `ExportClient.collect(ids)` 行为；新增批量入口，不改变既有单项调用方。测试可覆盖顺序、重复 ID、100 项上限、缺失项、单项失败、成功项保留、按项重试以及旧接口回归。

**优点：** 与当前内存式同步服务和客户端调用模型最匹配，接口和失败语义直接，延迟和运维成本低。
**缺点：** 批量大小和单请求耗时受同步处理限制；若未来单项检索变慢，需要增加超时和资源保护。

### 方案二：异步作业

新增创建作业接口，例如：

```text
POST /exports
GET /exports/:jobId
```

创建请求提交最多 100 个 ID，返回 `jobId`；调用方轮询作业状态，最终取得逐项结果。

它能隔离长耗时任务，但需要定义作业持久化、状态生命周期、过期清理、重复提交幂等性、轮询负载和失败重试语义。逐项结果仍需保留，不能把一个失败项提升为整个作业失败。兼容性方面，现有同步 API 仍须继续维护，系统同时承担两套生命周期。当前架构没有作业存储或进度模型，本轮也不需要异步进度查询，因此引入成本明显超出当前需求。

### 方案三：继续由客户端聚合

保持现有接口不变，让客户端继续逐个调用 `getDocument` 并聚合结果。

它的兼容性最好、服务端改动最少，现有逐项结果形状和重试逻辑可以延续。但一次导出最多需要 100 次网络或服务调用，批量吞吐、延迟、限流压力和一致性都由调用方承担；不同调用方还可能实现不同的并发、重试和部分失败策略。它没有形成服务端的批量公共契约。

## 推荐

推荐**方案一：同步批量入口**。

理由是它满足“一次请求拿到逐项结果”和“按项重试”这两个明确目标，同时能以增量方式保留现有单项接口。应将 100 项上限设为服务端公共契约，并让结果逐项、稳定、有状态，避免成功项被失败项遮蔽。异步作业可作为未来在同步耗时或规模约束无法满足时的独立设计；客户端聚合则继续作为旧客户端的兼容路径，而不是新的目标模型。

本轮未修改任何文件，且前一轮的工作区检查无变更。请确认是否选择**同步批量入口**；确认后再进入 Spec 身份与正式 Spec 流程。
