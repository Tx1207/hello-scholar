# Public batch retrieval API

## 1. 价值与当前决定

导出服务需要一次请求取得一批文档，同时保留每个输入项的独立结果，使缺失或失败项不会丢失成功项，调用方可以仅重试失败项。

当前决定是新增**同步批量公共接口**，单次最多处理 100 个文档 ID，并返回与输入逐项对应的结果。现有单文档接口继续保留，客户端聚合继续作为兼容路径；异步作业不属于本 Spec 的目标实现。

同步入口相比异步作业更符合当前服务的同步模型，避免引入作业存储、状态生命周期和进度查询。相比继续由客户端聚合，它将顺序、部分失败和上限等行为统一为服务端公共契约。

## 2. 问题与当前事实

当前事实：

- `src/retrieval-service.js` 的 `RetrievalService` 只提供 `getDocument(id)`。
- `clients/export-client.js` 通过循环调用单文档接口实现 `collect(ids)`。
- 当前客户端结果与输入逐项对应，缺失文档返回 `document: null`。
- Architecture 明确指出客户端当前拥有逐 ID 聚合和重试行为，服务端没有批量契约。
- `SPEC-013` 负责租户请求预算，不定义单项或批量响应合同。
- `SPEC-007` 负责副本读取一致性，不负责请求基数、部分失败或批量响应形状。
- 本能力需要独立的公共接口、数据结果和生命周期，能够独立批准、实施、验证和回滚。

需要解决的问题：

- 如何在一次请求中表达最多 100 个文档的逐项结果。
- 如何区分成功、缺失和可重试失败。
- 如何保证成功项不会因其他项失败而被丢弃。
- 如何在不破坏现有单文档调用方的前提下引入批量能力。
- 如何测试顺序、重复 ID、上限和部分失败行为。

## 3. 目标与非目标

### 目标

1. 提供同步批量检索公共接口。
2. 每次请求最多接收 100 个文档 ID。
3. 返回与输入逐项对应、保持输入顺序的结果。
4. 保留重复 ID 的重复结果，不由服务端静默去重。
5. 为每项明确表达成功、缺失或失败。
6. 单项失败不影响其他项结果。
7. 调用方可以根据逐项状态仅重试失败项。
8. 保持现有 `getDocument(id)` 及兼容客户端路径可用。
9. 与现有请求限流和副本一致性能力保持边界清晰。

### 非目标

- 不引入异步作业创建、轮询、进度查询或作业持久化。
- 不改变单文档 `getDocument(id)` 的既有语义。
- 不规定客户端必须删除或立即迁移其现有聚合逻辑。
- 不定义跨请求的批量幂等键或结果缓存。
- 不改变 `SPEC-013` 的请求预算规则。
- 不改变 `SPEC-007` 的副本选择和有界陈旧重试规则。
- 不扩展为任意数量文档的分页导出或后台大批量任务。

## 4. 目标设计

新增同步批量检索能力。调用方一次提交一组文档 ID，服务在同一请求生命周期内为每个输入项生成独立结果。

推荐的公共操作抽象为：

```text
batch retrieval(ids)
```

若通过 HTTP 暴露，则对应一个新的批量 route；具体 route 命名和传输封装应在实施 Plan 中落实，但不得改变本 Spec 定义的请求、结果和错误不变量。

处理规则：

1. 先验证请求整体是否满足批量协议。
2. 请求合法时，逐项检索输入 ID。
3. 某项成功、缺失或失败时，只更新该项结果。
4. 继续处理其他项，不因单项失败提前终止整个批量请求。
5. 按输入顺序返回逐项结果。
6. 请求整体错误仅用于无法建立逐项结果的情况，例如请求体非法、ID 数组为空或超过 100 项。
7. 单项失败必须保留稳定的错误代码，供调用方决定是否重试。
8. 现有单项入口继续提供原有单项行为；批量入口不是对旧入口的破坏性替换。

异步作业的取舍保留为未来方向：只有当同步处理的延迟、资源或规模约束无法满足时，才另行提出拥有独立生命周期的设计。客户端聚合保留为兼容方案，但不再是新增批量调用方的目标模型。

## 5. 接口、数据与不变量

### 请求接口

批量接口接收：

```js
{
  ids: string[]
}
```

约束：

- `ids` 必须存在且为数组。
- 数组长度必须为 `1` 至 `100`。
- 每个元素必须是有效文档 ID。
- 不得静默删除、排序或去重输入项。

### 逐项结果

每个输入项产生一个结果对象：

```js
{
  id: string,
  status: "ok" | "not_found" | "failed",
  document: object | null,
  error: object | null
}
```

状态不变量：

- `status: "ok"` 时，`document` 为文档副本，`error` 为 `null`。
- `status: "not_found"` 时，`document` 为 `null`，`error` 为 `null`。
- `status: "failed"` 时，`document` 为 `null`，`error` 含稳定错误信息。
- 每个结果的 `id` 等于对应输入项的 ID。
- 结果数组长度等于输入 `ids` 长度。
- 结果数组顺序等于输入顺序。
- 重复输入 ID 产生重复结果项。
- 一个 `failed` 项不得使其他成功或缺失项消失。
- 调用方可依据 `status` 和 `error.code` 选择性重试；重试不是服务端自动合并行为。

### 请求级错误

以下情况返回请求级错误，不生成部分结果：

- 请求体无法解析。
- `ids` 缺失、类型错误或包含非法元素。
- `ids` 为空。
- `ids` 超过 100 项。
- 服务在无法建立任何可信逐项结果时发生整体故障。

请求级错误必须与逐项 `failed` 状态区分，避免调用方把协议错误误认为可按项重试。

### 既有接口兼容性

- `RetrievalService.getDocument(id)` 保持返回文档副本或 `null` 的现有行为。
- `ExportClient.collect(ids)` 的现有逐项结果行为保持可用。
- 批量接口可以复用单项读取和现有一致性/限流能力，但不得改变其 owner 边界。
- 批量接口的错误结构不得要求旧客户端立即理解；旧调用方继续使用原接口。

## 6. 实施边界

实施范围包括：

- `src/retrieval-service.js`：增加批量检索能力，并保持现有单项方法不变。
- `clients/export-client.js`：仅在明确需要提供批量调用适配时修改；现有 `collect(ids)` 兼容行为必须保留。
- 公共 route 或接口适配层：新增批量请求和响应映射。
- `test/`：增加批量成功、缺失、失败、顺序、重复项、边界和兼容性测试。
- Architecture 或相关索引文档：仅在实施后公共边界确实变化时按既有文档流程更新。

必须保持不变：

- `SPEC-007` 的副本一致性策略。
- `SPEC-013` 的租户请求预算语义。
- 现有单文档接口的返回语义。
- 未被本能力要求的存储、认证和无关客户端行为。

本 Spec 不授权：

- 创建 Plan、Tasks 或直接修改源码。
- 引入异步作业数据库、队列、轮询 route 或后台 worker。
- 手工修改生成的 Specs Index。
- 修改既有 accepted Spec 的 owner 边界。

## 7. 验收与验证

### 功能验收

- 合法批量请求最多接受 100 个 ID。
- 输入 100 个 ID 时返回 100 个逐项结果。
- 输入顺序被完整保留。
- 重复 ID 产生对应数量的重复结果。
- 已存在文档返回 `ok` 和文档副本。
- 缺失文档返回 `not_found`，不影响其他项。
- 模拟单项读取失败时返回 `failed`，成功项仍然存在。
- 调用方能够筛选失败项并重新提交，而不必重取成功项。
- 空数组、超过 100 项、非法类型和非法 ID 被作为请求级错误拒绝。
- 现有 `getDocument(id)` 测试继续通过。
- 现有 `ExportClient.collect(ids)` 兼容测试继续通过。

### 契约和边界验证

- 逐项状态、`document` 和 `error` 的组合符合本 Spec 不变量。
- 单项失败与请求级错误可区分。
- 批量读取不会绕过 `SPEC-013` 的请求预算，也不会改变 `SPEC-007` 的一致性行为。
- 不存在异步作业状态或进度查询依赖。
- 文档检查、索引同步和最终 Spec Bundle 验证通过。

### 性能与回归验证

- 测试批量上限附近的请求行为。
- 测试包含成功、缺失、失败和重复项的混合批次。
- 验证批量入口的失败隔离。
- 验证旧客户端在批量能力加入后仍可工作。
- 若实现引入并发或内部优化，必须证明其不改变结果顺序和逐项错误语义。

## 兼容性与未来演进

本 Spec 采用新增入口而非替换单文档入口，因此旧调用方可以继续逐项调用。客户端聚合的存在不构成批量接口的反向依赖；新调用方应优先使用同步批量接口，以获得一致的逐项结果和重试合同。

如果未来需要处理超过 100 项、长时间运行或跨请求进度，必须另行评估异步作业作为独立设计。该设计不得在没有新 Spec 或明确 revision 的情况下修改本 Spec 的同步批量不变量。

## 条件性风险与取舍

同步批量将单次请求的工作量集中到服务端，可能受到总耗时、资源占用和限流预算影响。实现必须在不改变逐项结果合同的前提下使用超时和资源保护；若保护机制导致整体无法建立可信结果，应返回请求级错误。

异步作业能处理更长生命周期，但会引入作业状态、持久化、清理和轮询合同；这些当前需求未要求，因此明确延后。客户端聚合改动最少，但继续分散延迟、重试和限流行为，因此保留为兼容路径而非推荐目标。
