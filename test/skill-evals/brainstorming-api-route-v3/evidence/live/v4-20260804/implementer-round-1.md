## 三种方向比较

### 方案一：新增同步批量入口

新增独立的批量导出接口，例如：

```text
POST /exports/batch
请求：{ "ids": ["doc-1", "doc-2", ...] }
响应：{
  "results": [
    { "id": "doc-1", "status": "succeeded", "document": { ... } },
    { "id": "doc-2", "status": "not_found", "document": null },
    { "id": "doc-3", "status": "failed", "error": { ... } }
  ]
}
```

建议约束：

- `ids` 数量必须为 1–100，超过上限在任何文档读取前拒绝。
- 响应逐项对应输入，保持输入顺序；重复 ID 的处理规则需固定，建议保留重复项以保持逐项语义。
- 单项缺失使用稳定的 `not_found` 状态；单项读取错误使用 `failed` 状态和机器可判定的错误码。
- 整体请求只有在请求级校验失败、鉴权/限流失败等情况下失败；单项失败不影响其他项。
- 调用方可只重试 `failed` 项；`not_found` 默认不应自动重试。
- `SPEC-007` 继续负责每项读取的一致性，`SPEC-013` 负责请求级预算；批量请求的成本计量需要在新契约中明确，不能隐含改变现有单查语义。

**兼容性**

- 保留现有单文档 `getDocument(id)` 和当前 `ExportClient.collect(ids)` 的行为，避免已有调用方被迫迁移。
- 新批量入口应是新增公共契约，而不是改变单查返回值或让客户端自动切换。
- 客户端可逐步改为调用批量入口，并将逐项状态转换为现有结果模型。

**优点**

- 完全满足“一次请求拿到逐项结果”和“按项重试”。
- 生命周期简单，易于观察、测试和回滚。
- 服务端可以统一执行批量上限、请求预算和错误分类。

**代价**

- 单次请求处理最多 100 项，延迟和响应体大小随批量增长。
- 需要定义批量读取的并发、超时、取消和预算消耗规则。

---

### 方案二：异步作业

新增作业创建、状态查询、结果获取等接口：

```text
POST /export-jobs
GET /export-jobs/{jobId}
GET /export-jobs/{jobId}/results
```

作业结果同样按项记录成功、缺失和失败。

**兼容性与部分失败**

- 可以天然保留已完成成功项，并允许失败项独立重试。
- 但需要引入作业持久化、状态生命周期、过期策略、幂等键、结果保留和权限校验。
- 这会改变调用方交互模型，与当前“单次请求拿到结果”的明确要求不符。

**结论**

该方案适合大批量、长耗时或需要断点续作的场景，但在本轮固定上限 100 且不需要进度查询时，明显过度设计。因此不推荐作为当前批量导出的首选。

---

### 方案三：继续由客户端聚合单项请求

不增加服务端批量入口，继续让 `ExportClient` 逐个调用 `getDocument(id)`，客户端负责聚合、错误分类和重试。

**兼容性与部分失败**

- 对现有服务端接口改动最小，单项失败天然不会丢失其他已完成结果。
- 客户端可以按项重试，但不同调用方必须各自实现一致的重试、并发、超时和错误映射。
- 服务端无法统一保证批量上限、请求级预算、批量观测和跨项资源保护。
- 当前客户端已有逐项聚合行为，但当前服务接口找不到文档只返回 `null`，尚无统一的“缺失”和“读取失败”公共错误契约。

**优点**

- 迁移成本最低。
- 不需要新服务端生命周期。

**代价**

- 请求次数最多 100 倍，延迟和网络开销更高。
- 各调用方容易产生不一致的部分失败和重试语义。
- 无法真正形成统一的批量公共接口。

---

## 推荐决定

推荐**方案一：新增同步批量入口**，同时保留现有单项入口和现有客户端兼容行为。

目标契约应明确：

1. 批量请求最多 100 个 ID。
2. 请求成功时返回逐项结果，并保持输入顺序。
3. 每项必须是成功、缺失或失败之一；单项失败不能使其他成功项消失。
4. 单项失败结果包含稳定错误码，使调用方能仅重试可重试项。
5. 请求级失败与单项失败严格区分。
6. 现有单查和客户端聚合接口不改变语义。
7. 新契约补充批量请求的限流计量、并发/超时边界及可观测字段。
8. 测试覆盖：上限边界、空输入、顺序与重复 ID、全成功、混合成功/缺失/失败、请求级失败、按项重试，以及旧单查和客户端行为回归。

刻意不纳入本轮：异步作业生命周期、进度查询、后台队列、结果持久化和客户端强制迁移。

**请确认是否批准以上“新增同步批量入口、保留现有单项契约”的设计决定；在获得确认前我不会创建或修改 Spec。**
