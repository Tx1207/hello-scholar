基于当前约束：

- 批量上限固定为 100；
- 一次请求需要拿到逐项结果；
- 单项缺失或失败不能影响其他成功项；
- 调用方必须能按项重试；
- 本轮不需要异步进度查询；

有三种方向。

### 方案 A：同步批量入口（推荐）

新增独立的批量公共方法，例如：

```js
retrievalService.getDocuments(ids)
```

请求结果按输入顺序逐项返回，每项携带明确状态：

```js
[
  { id: "doc-1", status: "fulfilled", document: { ... } },
  { id: "missing", status: "not_found", document: null },
  { id: "doc-3", status: "failed", error: { code: "..." } }
]
```

关键约束：

- `ids.length` 必须在 1–100；
- 保留输入顺序和重复项，避免调用方无法对应结果；
- 批量请求本身成功表示“逐项结果已生成”，不表示每项都成功；
- `not_found`、可重试失败和不可重试失败必须区分；
- 每项结果含稳定的 `id` 和机器可判断的 `status` / `error.code`，调用方可只重试失败项；
- 现有 `getDocument(id)` 保持不变，旧客户端继续工作；
- `ExportClient.collect` 可以迁移为一次批量调用，但迁移不是公共单项接口的破坏性替换。

部分失败最清晰：HTTP/方法层返回批量结果，单项失败封装在对应 item 内；只有批量参数非法、请求预算拒绝等请求级错误才整体失败。`SPEC-013` 的预算计费方式需要在新 Spec 中明确为一次批量请求还是按项计费，但不应把这两种语义混在响应合同里。

测试重点：

- 1、100、101 个 ID；
- 全部成功、全部缺失、成功与缺失混合；
- 单项异常不影响其他项；
- 输出顺序、重复 ID 和逐项错误码；
- 仅重试失败项；
- 旧 `getDocument` 与旧客户端行为不变；
- 请求级拒绝不触发任何读取；
- 与 `SPEC-007` 的副本一致性行为逐项兼容。

### 方案 B：异步批量作业

提交请求后返回 `jobId`，再通过查询接口获取逐项结果。

优点是适合大规模或长耗时任务，未来可扩展进度和持久化重试。缺点是当前明确需要一次请求拿到结果，且不需要进度查询；它会额外引入作业生命周期、过期、幂等、查询权限、存储和清理合同，明显扩大范围。即使不实现进度查询，也无法避免客户端等待和作业状态语义，因此不适合当前需求。

### 方案 C：继续由客户端聚合

保持单项公共接口，由 `ExportClient` 并发或循环调用最多 100 次。

优点是服务端改动最小，单项重试逻辑天然可复用。缺点是网络往返和限流成本按项放大，客户端必须处理并发控制、顺序、重复项和错误分类；不同客户端容易产生不一致行为。它也无法实现“服务一次取一批文档”的核心目标，只是把批量语义留在调用方。

### 建议

采用**方案 A：同步批量入口**，并将其作为独立的批量生命周期和公共接口合同；保留单项接口作为兼容路径。设计确认后应建立一个新的独立 Spec，而不是修改 `SPEC-007` 或 `SPEC-013`：前者只负责存储一致性，后者明确不定义批量响应合同。

如果你批准这个方向，我下一步会按指定流程确定新 Spec 的 canonical 身份、写入正式 draft Spec、完成整文件审核并在 accepted 后转交 `$writing-plans`；本轮不会直接改源码或生成 Tasks。
