# SPEC-014：公共批量检索 API

## 1. 价值与当前决定

导出服务可以通过一次同步批量请求取得一组文档的逐项结果，避免客户端为每个文档分别发起请求，同时保留成功项并支持对缺失或失败项按项重试。

当前决定是新增同步批量公共入口，单次最多接收 100 个文档 ID，并返回与输入逐项对应的结果。输入顺序和重复项都必须保留。单项缺失或失败不得使其他项失败；只有请求级错误才使整个批量请求失败。

现有单文档入口继续保留，确保已有调用方可以兼容运行。异步作业和继续由客户端聚合作为候选方向保留在本 Spec 的取舍记录中，但不属于本次目标设计。

## 2. 问题与当前事实

### 已观察到的项目事实

- `src/retrieval-service.js` 当前提供 `getDocument(id)`，返回文档副本或 `null`。
- `clients/export-client.js` 当前逐个调用 `getDocument`，并按输入 ID 生成结果。
- 当前客户端行为保留每个输入 ID，包括缺失项；缺失项的 `document` 为 `null`。
- `test/retrieval-service.test.js` 已覆盖单项成功、单项缺失，以及客户端逐项聚合行为。
- `SPEC-013` 负责在检索工作开始前执行租户请求预算，不定义单项或批量响应合同。
- `SPEC-007` 负责副本读取一致性，不定义 HTTP 请求基数、部分失败或批量响应形状。
- 当前不存在批量公共合同。
- 用户已确定批量上限固定为 100、需要一次请求获得逐项结果、成功项不可因单项缺失或失败而丢失，并且调用方必须能够按项重试。
- 本次设计不需要异步进度查询。

### 待通过实现验证的行为

- 批量服务如何在内部调度单项读取，以及如何复用 `SPEC-007` 定义的逐项一致性行为。
- `SPEC-013` 对批量请求的预算计费单位；该决定必须与本 Spec 的请求级错误行为集成，但不改变逐项结果格式。
- 运行时具体异常如何映射为稳定的逐项错误码及可重试性。

## 3. 目标与非目标

### 目标

1. 提供一个同步批量公共入口，一次最多处理 100 个文档 ID。
2. 为每个输入项返回独立结果。
3. 保留输入顺序和重复项。
4. 允许成功项与缺失项、失败项同时存在。
5. 为调用方提供稳定的逐项状态和错误码，使其能够只重试可重试项。
6. 保持现有 `getDocument(id)` 行为不变。
7. 使 `ExportClient` 能够通过一次批量调用获得与现有逐项输出等价或更丰富的结果。
8. 覆盖参数边界、部分失败、兼容性、限流和一致性相关测试。

### 非目标

1. 不在本次设计中引入异步作业、作业持久化、进度查询或作业清理生命周期。
2. 不移除或破坏现有单文档入口。
3. 不改变 `SPEC-007` 的副本选择和有界陈旧读取规则。
4. 不重新定义租户请求预算的总体策略；批量请求的计费单位需与 `SPEC-013` 的实现边界协调。
5. 不提供跨批次的服务端重试队列或服务端幂等作业。
6. 不扩大单次请求上限到 100 以上。
7. 不进行与批量接口无关的客户端或服务重构。

## 4. 目标设计

### 4.1 公共入口

在检索服务上新增同步批量入口：

```js
getDocuments(ids)
```

该入口接收文档 ID 数组，完成本次批量请求后直接返回完整的逐项结果。批量入口不返回异步任务 ID，也不要求调用方进行进度轮询。

`getDocument(id)` 继续作为现有单文档入口存在。

### 4.2 数据流

1. 调用方传入 1–100 个 ID。
2. 批量入口验证请求级输入约束。
3. 对每个输入项执行独立的文档读取。
4. 每项读取遵循 `SPEC-007` 的副本一致性规则。
5. 单项读取结果被转换为稳定的逐项状态：
   - 成功；
   - 未找到；
   - 失败。
6. 批量入口按原始输入顺序组装结果。
7. 调用方可以保留成功结果，并从结果中筛选需要重试的项。

单项失败不得中止剩余项的读取，也不得使已经成功的项消失。

### 4.3 请求级错误

以下错误属于请求级错误，整个批量请求失败，不产生部分响应：

- `ids` 不是有效的 ID 数组；
- `ids` 为空；
- `ids` 超过 100 项；
- 请求在检索开始前被 `SPEC-013` 的预算规则拒绝。

请求级拒绝不得执行存储读取。

### 4.4 逐项错误

逐项错误只影响对应输入项。其他项仍必须返回结果。

- 未找到是明确的 `not_found` 状态，不视为请求级失败。
- 可重试的读取异常必须返回稳定错误码，并标记为可重试。
- 不可重试的读取异常必须返回稳定错误码，并标记为不可重试。
- 错误信息不得要求调用方解析自然语言文本来判断状态。

### 4.5 客户端迁移

`ExportClient.collect(ids)` 可以改为调用 `getDocuments(ids)`，但它必须继续提供每个输入 ID 的对应结果。客户端可以根据逐项状态选择：

- 直接返回成功项；
- 报告或保留缺失项；
- 只对可重试失败项重新调用批量入口或单项入口。

客户端不应通过隐藏失败项来制造“全部成功”的结果。

## 5. 接口、数据与不变量

### 5.1 输入

```js
getDocuments(ids)
```

约束：

- `ids` 必须是数组；
- 数组长度范围为 1–100；
- ID 的合法性沿用现有单文档入口的边界；
- 重复 ID 不去重；
- 输入数组的顺序具有语义。

### 5.2 输出

每个输入项对应一个结果对象。推荐形状如下：

```js
[
  {
    id: "doc-1",
    status: "fulfilled",
    document: {
      id: "doc-1",
      text: "alpha"
    }
  },
  {
    id: "missing",
    status: "not_found",
    document: null
  },
  {
    id: "doc-3",
    status: "failed",
    error: {
      code: "RETRIEVAL_FAILED",
      retryable: true
    }
  }
]
```

字段约束：

- `id` 必须等于对应输入位置的 ID；
- `status` 必须是稳定的机器可判断值；
- `fulfilled` 结果包含 `document`；
- `not_found` 结果包含 `document: null`；
- `failed` 结果包含结构化 `error`；
- `retryable` 必须是布尔值；
- 不应同时在同一项中返回成功文档和失败错误。

### 5.3 结果对应关系

对输入：

```js
["doc-1", "missing", "doc-1"]
```

输出必须包含三个结果，顺序相同；两个 `doc-1` 不得因去重而合并。结果数量必须始终等于输入数量。

### 5.4 成功与部分失败

批量请求的成功语义是“服务已生成全部逐项结果”，而不是“所有文档都读取成功”。

因此：

- 全部成功是合法结果；
- 全部缺失是合法结果；
- 成功、缺失和失败混合是合法结果；
- 单项失败不得丢弃其他结果；
- 只有请求级错误才返回整体失败。

### 5.5 重试不变量

调用方必须能依据逐项状态筛选重试集合：

```js
results.filter((result) => result.status === "failed" && result.error.retryable)
```

重试只应针对选中的失败项，不要求重新提交已经成功或明确未找到的项。服务端不负责保存或执行该重试集合。

### 5.6 兼容性不变量

- `getDocument(id)` 的现有返回值和缺失语义保持不变。
- 现有单项调用方无需迁移即可继续运行。
- 批量接口不能要求旧客户端理解异步任务状态。
- `ExportClient` 的既有成功、缺失和输入顺序语义必须得到保留；新增失败状态时应采用结构化扩展，而不是静默丢弃项。

## 6. 实施边界

### 纳入范围

- `src/retrieval-service.js`：新增同步批量入口及逐项结果组装。
- `clients/export-client.js`：迁移导出路径以使用批量入口，同时保留逐项结果和按项重试所需信息。
- `test/retrieval-service.test.js`：补充批量输入、输出、部分失败、重试筛选和兼容性测试。
- 与请求预算集成所需的最小边界适配，遵循 `SPEC-013` 的既有职责。
- 与副本一致性集成所需的最小边界适配，遵循 `SPEC-007` 的既有职责。
- 新增批量 API 的正式接口文档和验收证据。

### 保持在范围外

- 不修改 `SPEC-007` 的存储一致性规则。
- 不修改 `SPEC-013` 的总体限流目标；若预算单位需要产品级选择，应单独形成设计决定或 Spec 修订。
- 不新增异步作业存储、作业查询端点、进度事件或后台队列。
- 不移除单文档入口。
- 不重写与本能力无关的客户端或服务实现。
- 不手工编辑生成的 Spec Index。
- 不在本 Spec 中创建 Plan、Tasks 或直接实施源码。

## 7. 验收与验证

### 公共接口验收

- 批量入口接受 1 个 ID。
- 批量入口接受 100 个 ID。
- 101 个 ID 被作为请求级错误拒绝。
- 空数组和无效输入被作为请求级错误拒绝。
- 请求级拒绝不执行任何存储读取。

### 逐项结果验收

- 全部成功时，每个输入 ID 都有成功结果。
- 混合成功和缺失时，成功项保留，缺失项返回 `not_found`。
- 混合成功和失败时，成功项保留，失败项返回结构化错误。
- 单项失败不会中止或丢弃其他项。
- 输出顺序与输入顺序一致。
- 重复输入项产生重复的逐项结果。
- 输出数量始终与输入数量一致。

### 重试验收

- 调用方可以通过结构化状态筛选失败项。
- 只有标记为 `retryable: true` 的失败项进入按项重试集合。
- 成功项无需重试。
- `not_found` 不被误判为可重试读取失败。
- 重试集合可以独立提交，不需要重新提交整个原始批次。

### 兼容性验收

- 现有 `getDocument(id)` 测试继续通过。
- 旧单项调用方的成功和缺失行为不变。
- `ExportClient.collect` 仍为每个输入 ID 返回对应结果。
- 客户端迁移到批量入口后不静默丢弃任何逐项结果。

### 规范集成验收

- 批量项读取遵循 `SPEC-007` 的副本一致性和主库回退规则。
- `SPEC-013` 拒绝的请求在任何文档读取前终止。
- 批量响应合同不承担存储选择或租户预算策略的定义职责。

### 测试策略

使用现有 Node 测试框架补充接口测试和客户端行为测试。测试应覆盖边界、混合结果、重复项、单项失败隔离、错误码与重试筛选；不需要为本次同步入口引入异步进度测试。

## 候选方案与权衡

### 同步批量入口：当前推荐

一次请求直接返回最多 100 个逐项结果，最符合导出服务的一次请求需求。它增加服务端公共合同和部分失败处理，但可保持单项接口兼容，并把顺序、结果对应和错误分类统一在服务层。

### 异步作业

异步作业适合耗时更长、规模更大的处理，可为未来进度查询和持久化重试提供基础。但当前需求明确要求一次请求拿到逐项结果且不需要进度查询；引入作业 ID、状态生命周期、查询权限、过期和清理会扩大公共接口和运维边界，因此本次不采用。

### 继续由客户端聚合

客户端聚合改动服务端最少，并且可以复用单项读取。但它会将并发控制、请求放大、顺序保持、错误分类和按项重试继续分散到调用方，无法实现服务一次取一批文档的目标，因此本次不采用。

## 条件章节：材料性风险与控制

### 批量请求预算语义

一次批量请求应如何消耗 `SPEC-013` 的租户预算，可能影响限流容量和兼容性。该语义必须在实施前明确，并确保被拒绝的批量请求不触发任何存储读取；它不应改变逐项结果合同。

### 逐项错误分类稳定性

如果底层异常直接暴露为不稳定的自然语言消息，调用方将无法安全地按项重试。实现必须提供稳定错误码和明确的 `retryable` 标记，并通过测试固定其行为。

### 单项读取隔离

批量执行不能因一个同步异常或读取失败而提前退出。实现和测试必须证明单项失败不会阻断后续项，也不会改变结果顺序。

### 批量大小与延迟

上限固定为 100，但批量请求仍可能带来更高的单请求延迟。实现应在测试中验证 100 项边界的可接受行为；本 Spec 不引入异步化作为性能兜底。
