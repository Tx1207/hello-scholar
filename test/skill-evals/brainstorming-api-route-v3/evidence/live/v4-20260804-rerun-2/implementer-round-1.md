你确认了：批量上限固定为 100；导出服务需要一次请求取得逐项结果；单项缺失或失败不能影响成功项；调用方必须能按项重试；本轮不需要异步进度查询。我会基于已检查的项目事实比较三种方向，不写入任何文件，也不启动后续轮次。

## 三种方向比较

### 方案一：同步批量入口

新增一个公共批量检索接口，一次接收最多 100 个文档 ID，并在一次响应中返回逐项结果。

**公共接口方向**

- 新增独立的 batch route / service method。
- 输入包含一组文档 ID，硬上限为 100。
- 响应按输入项返回结果，使调用方能通过 ID 定位并单独重试。
- 每项至少区分成功、文档不存在、单项检索失败及其可重试信息。
- 整体请求只在请求级错误时失败；单项失败不能丢弃其他结果。

**优点**

- 直接满足“一次请求拿到逐项结果”。
- 与现有 `getDocument(id)` 和客户端返回结构最接近，迁移边界清晰。
- 失败项天然可按项重试，不需要额外作业状态或结果存储。
- 测试可以覆盖顺序、缺失、混合成功/失败、上限和重试选择。

**代价与风险**

- 一次请求内的 100 项会共享请求级超时、限流和资源预算，需要明确既有规则如何计量。
- 需要定义批量响应顺序、重复 ID、错误分类和单项重试提示。
- 批量接口是新的公共契约，不能只把客户端循环搬到服务端。

### 方案二：异步批量作业

客户端提交最多 100 个 ID，服务端创建作业，之后通过作业查询或结果下载取得逐项结果。

**优点**

- 可以把处理时间、重试和资源消耗从初始请求中解耦。
- 适合未来批量规模或处理时间显著增长的情形。

**代价与风险**

- 当前需求明确不需要异步进度查询，会引入没有当前价值的作业生命周期。
- “一次请求拿到逐项结果”无法直接满足。
- 需要新的持久化、失败恢复和权限边界；当前项目没有事实依据。

### 方案三：继续由客户端聚合单项调用

保持服务端只有 `getDocument(id)`，由 `ExportClient` 继续逐 ID 请求并聚合结果。

**优点**

- 不增加公共服务端接口。
- 现有按项重试模型最容易保持兼容。
- 实施和回滚成本最低。

**代价与风险**

- 不满足“一次请求拿到逐项结果”的目标。
- 100 个 ID 会产生最多 100 次服务调用。
- 不形成可复用的批量公共能力。

## 推荐

推荐**方案一：同步批量入口**，将其定义为独立批量能力。

1. 请求最多 100 个 ID。
2. 一次请求返回全部逐项结果并保持输入可关联性。
3. 缺失项和失败项逐项返回，成功项始终保留。
4. 客户端只重试失败项。
5. 异步作业、进度查询、持久化和下载生命周期不纳入本次范围。
6. 保留现有单项接口以维持兼容。
