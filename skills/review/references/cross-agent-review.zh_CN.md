# 跨 Agent 审查

交给审查者稳定的对象和足以独立判断的证据。用户要求另一模型，或已有授权下的独立视角能够解决重要不确定性时使用；不要求每项任务都调用第二个模型。

## 准备审查材料

提供源材料，不预设作者希望得到的结论。交代：

- 要检查的问题及具体方案、变更或证据。Spec 注明路径与 Revision；代码注明现有提交及范围内的工作树变更。审查其他对象不要求建立 Spec。
- 用户目标、已确认约束，以及必要的支撑文件或直接证据。影响结论的反向结果一并提供，缺失的证据如实说明。
- 本轮使用的代码、输入和 Run 结果的实际状态。仅有 Spec Revision 不能标识它们的全部状态。
- 可读范围、允许的检查及指定输出位置。审查者不能修改被审查的设计、代码、实验或生成导航。
- 要求返回有实质影响的发现及其触发条件、依据、后果和最小处理方向；区分已确认缺陷与待验证疑点，说明重要覆盖限制。

审查期间保持输入稳定。沿用已有 Git 引用、有明确范围的 diff，或当前文档及状态说明；不引入指纹服务或复制整个项目。输入在审查期间变化时，明确实际采用哪组材料，并限定受影响结论。不能将混合状态描述为一次完整验证。

## 如实使用可用客户端

用户指定 Claude、Codex 或其他模型时，通过可用且获授权的工具调用该客户端。沿用本任务已有授权；模型调用费用或远程执行仍需在授权范围内。注明实际审查者和已知的模型信息。同模型 subagent 的执行不能证明已经运行了用户要求的另一模型。

需要的客户端或访问方式不可用时，返回可直接使用的审查请求，带具体路径、输入状态、目的和输出说明，并明确指定审查尚未执行。不自行安装客户端、获取凭据，或用原模型名称描述实际替代的模型。

例如，可按实际材料改写以下请求：

> 审查 `<方案路径>` 的 `<Revision 或当前状态>`，重点判断 `<决定或风险>`，依据为 `<支撑材料路径及状态>`。读取必要关联材料，只执行 `<允许的检查>`。将发现写入 `<已授权输出位置>`；未要求文件时直接返回正文。保持被审查材料不变。说明每项实质问题的触发条件、证据、后果和最小处理方向，区分已确认问题与未决疑点，注明实际检查内容和未验证范围。

占位项说明交接所需信息，不要求审查结果采用这些标题。只提供任务所需内容，不把秘密作为审查上下文。

## 保留每轮审查实际建立的结论

保存 Spec 审查属于任务范围时，使用 `spec.md` 同目录的 `review.md`。其他对象沿用项目已有评审位置或在对话中返回。采用普通 Markdown，不增加新 schema、必需 Index 或并行任务 tracker。

按轮次记录对象与输入状态、日期、实际审查者、发现和覆盖范围。审查者在指定位置写发现；主 Agent 记录采用、说明理由的不采用，或仍需核实的具体事实，并在原授权内把产生的决定整合回相关 Spec。

多 Agent 并发时，同一时刻每份文件只有一个写入者。合并另一 Agent 完成的输出前，读取最新内容。如果主 Agent 与审查者都需要改评审文件，审查者可以先返回发现，由主 Agent 保存。

后续 Spec 修订不会改变旧审查实际检查的版本。即使 Spec Revision 不变，代码、输入数据或 Run 结果改变，也可能使原审查不再覆盖当前状态。依据变化的证据复查受影响判断，不默认重复无关检查。多个审查者一致只支持讨论，不能证明方案已经采用或实验已经有效。
