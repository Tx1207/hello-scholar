# Review

找出哪些情况会使当前决定失去依据，或让所需行为在实际条件下失败。用独立推导的预期、具体反例和证据，区分实质问题、未决疑点与偏好。

审查默认只读，不要求已有 Spec。用户要求审查并修复时，先确认发现，再在已有授权内继续修复和相关验证，不插入新的阶段审批。

## 明确判断覆盖什么

从请求和现有上下文确定对象与目的：方案、指定变更、实现或研究证据。说明实际检查的当前状态。Spec 保留路径、Revision 和状态；代码沿用现有提交与相关工作树变更；证据注明实际输入、Run Record 和结果。不要求新建提交或身份系统。

阅读对象及理解它所需的关联材料。按方案评估方案，尚未编写代码本身不构成设计缺陷。Draft 和部分实现同样可以审查。只有不同解释会改变审查范围时，才澄清缺失的范围。

审查期间保持源码、测试、Spec、Run Record、Architecture 和生成的 Index 不变。只运行已有授权内的相关检查，将临时输出与被审查材料隔离。实验与付费调用必须在覆盖这些动作的授权范围内，普通审查不扩展授权。只有用户要求保存或原任务已包含保存时，才在指定评审位置写发现。

## 质疑会影响结论的假设

从用户目标、已确认规则和真实外部契约出发，独立于实现及其测试推导预期行为。这些来源相互矛盾时，说明冲突，不选择恰好能让当前工作通过的解释。

沿着会改变结论的关系检查：

- 对方案，将承诺的结果与实现机制、成立假设、资源限制及必要交互联系起来。寻找设计无法应对的现实情境，并说明它违背了哪项承诺。
- 对代码，沿相关调用方追踪输入、状态变化、失败和输出，确认疑似触发条件可达、后果确实成立。外观相似或多一层结构本身不能证明复杂性多余，要辨认它承担的职责或真实契约。
- 对研究，判断比较和测量能否支持所声称的解释。区分运行失败、暂不能判断的比较、有效负结果和支持采用的证据。关注条件不兼容、遗漏反向结果，或证据尚未排除的其他解释。

优先检查最可能实质影响正确性或下一步选择的假设。针对性检查可以解决疑问时就使用，不扩展成无边界审计，也不凑发现数量。

报告缺陷前，核实触发条件、相关证据和后果。有合理担忧但证据不足时，写成需要某项具体检查解决的疑点，不写成已经成立的失败。已有注释、测试通过、另一模型同意和旧总结，均不能单独证明结论。明确当前代码检查或本次执行实际证明了什么。

缺少报告或证据链接不能证明某次执行从未发生。有相关直接证据时核对；否则说明从已检查材料中无法验证该主张。区分文档缺失、验证缺口与已经证实的失败。

## 有 Spec 时对照验收

对每个关键 `AC-NN`，判断满足、部分满足、缺失、冲突或无法验证，并指出依据。紧密相关的项目可以合并说明，但不能隐藏缺口。

关键用户行为应注明实际验证的 CLI、API、UI 或调用方入口，以及仍未验证的部分。检查通过只支持其覆盖范围。验收规则本身有误时单独报告，不改写 Spec 来迁就实现。

`hello-scholar docs check` 可用且与审查有关时运行。检查失败属于证据，不阻止继续对照其他部分。只有明确检查尚未迁移的历史 Bundle 时才参考旧 Plan/Tasks；它们不控制当前执行。

## 返回读者可以判断的结论

先报告实质发现。用相连的自然语言解释问题、触发条件、实际后果、直接依据和最小修复或验证方向。需要讨论或追踪发现时使用稳定标识，不为每句话拆一个字段。

说明对象及状态、实际完成的有效检查，以及限制结论的边界。没有证据支持实质发现时，在该范围内如实说明。未经验证的风险不等于缺陷，没有发现也不证明所有行为都正确。

区分已经采用的决定与拟议修改。审查中的建议本身不会修订设计，也不代表已经采用。

由另一 Agent 或模型独立审查，或审查需要在之后接续时，读取[跨 Agent 审查](references/cross-agent-review.zh_CN.md)。主 Agent 负责整合与处理发现，审查者只负责指定的审查输出。
