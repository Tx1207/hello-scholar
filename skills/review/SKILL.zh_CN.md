# Review

找出在实际条件下可能使拟议决定失效或破坏必需行为的问题。用独立的预期、具体反例和证据，把实质问题与未决问题或个人偏好区分开。

审查默认只读，不需要 Spec。用户要求审查并修复（review and repair）时，先确定发现，再继续修复和相应验证。

## 明确判断覆盖什么

确定审查对象和实际检查的状态：Spec 的路径、修订和状态；代码的提交和范围内的工作区改动；证据的输入、Run Record 和结果。阅读理解对象所需的相关材料。把方案当作方案评判：尚未编写的代码不是设计缺陷。保持被审查材料和生成的 Index 不变，只运行已有授权覆盖的检查。

## 质疑影响结论的假设

从用户目标、已确认规则和真实契约推导应有的结果，独立于实现及其测试。这些来源相互矛盾时，指出矛盾，不选择能让工作通过的版本。

- 设计：把它的承诺连接到实现承诺所需的机制、假设、资源限制和相互作用，寻找它无法处理的现实情形。
- 代码：沿相关调用方追踪输入、状态变化、失败和输出。确认可疑触发条件可达、后果确实发生。相似代码或多一层封装，只有在确认它不承担任何职责或契约时才算不必要的复杂性。
- 科研：检查比较与测量是否支持所声称的解释。区分执行失败、比较不确定、有效负结果和支持采用的证据；寻找不兼容的条件、被省略的相反结果或尚未排除的其他解释。检查在启动新 Run 之前，是否已有 Run 本可回答这个问题。

优先追查对正确性或下一步决定影响最大的假设；不扩展成全面审计，也不凑发现数量。报告缺陷前，核实其触发条件、证据和后果；否则作为问题提出，并写明能确定它的检查。缺少报告不能证明执行从未发生；测试通过、另一个模型的认同或旧总结也不能证明主张成立。

## 提供 Spec 时对照验收

对每个重要的 `AC-NN`，判断它是满足、部分满足、缺失、矛盾还是无法验证，并指向支持判断的证据。对重要的用户可见行为，写明实际经过的入口和仍未验证的部分。验收规则本身有误时单独报告，不改写 Spec 去迁就实现。

## 报告

先写实质发现。每条说明问题、触发条件、实际后果、直接证据，以及最小的修复或验证方向；发现需要讨论时使用稳定编号。写明审查的对象与状态、实际执行的检查和判断的边界。没有有依据的实质发现时，在该范围内如实说明；没有发现不等于证明正确。审查中的建议本身不修订设计。

由另一个 Agent 或模型审查，或审查之后需要续做时，阅读 [跨 Agent 审查](references/cross-agent-review.zh_CN.md)。
