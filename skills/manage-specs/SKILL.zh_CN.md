# Manage Specs

保存一份让其他读者看得懂的设计：要改变什么、为什么这个选择由证据推出、如何判断结果。仅列出准备做的动作还不够，要把目标、决定、约束和后果之间的关系写明。

目的和具体做法明确后，就把可审阅的方案存为 draft，并写入重要未决问题；不必等所有选择都确定。

## 选择归属

先查已知设计路径，再用 Index 或定向搜索。完整阅读可能的归属文档，以及相关 Architecture、代码、测试和证据。已有项目文档归属时沿用它，不新建相互竞争的 Spec。对 hello-scholar Spec：

- **Revise**：已有一个 Spec 拥有相同能力和生命周期。
- **Create**：该能力有独立价值、验收边界和生命周期。
- **Replace**：目标设计将替代已采用的契约或实现模型。

按决定的职责和存续时间选择，而不是按修改的文件数。只有两个同样合理的归属会实质改变设计时，才问一个聚焦问题。

新 Spec 取全局下一个编号（计入 rejected 和 superseded 的 ID，至少三位），沿用已有 Topic 或 Architecture 与调用关系表明的窄能力边界，名称描述稳定的公开能力而不是所选实现方式：`hello-scholar/specs/<topic>/SPEC-NNN-<name>/spec.md`，例如 `batch-retrieval/SPEC-004-public-batch-retrieval-api`。

## 把设计写成连贯的论证

先写当前推荐或已接受的决定、改变的对象与行为，以及决定性理由。把问题连接到具体设计：每个决定和状态归谁负责、数据和控制如何流动、调用方看到什么、失败意味着什么。写出必要的实施顺序及每个有意义步骤的检查。重要替代方案通过排除它的取舍来解释。

区分已确认事实、假设、已接受决定和未决选择，并说明做法的哪部分依赖哪项不确定性。修订时保留仍然有效的约束；不要用补丁说明替换完整设计，也不要悄悄把建议变成要求。

科研设计把问题连接到能改变下一步选择的比较：对照与干预、数据和评价条件、控制、重复、解释规则、预算和停止条件。写明设计复用了哪些已有 Run 和产物，以及与它们有何差异。跨 Run 结论保存在这里，并链接到对应 Run。

从用户目标、已确认的业务规则和真实外部契约推导可观察的验收，而不是从当前代码输出推导。在稳定的 `AC-NN` 标识旁记录当前证据及其边界，先在 Spec 中把重要发现讲清楚，再链接检查、审查或 Run。

## 维护身份与当前含义

使用 `schema: 1`。尚未确定的设计以 `draft` 开始。用户接受或明确要求实施该修订、且重要未决决定已解决时，进入 `accepted`；实施进度不增加状态。只有当前修订的每个验收要求都有当前证据时，才设为 `completed`。

范围、行为、接口、约束或判断标准变化时递增 `revision`，并同时更新受影响的设计和验收。只补证据、格式、日期或生命周期时不递增。后来的修订不改写过去 Run 的条件或记录的修订。

替代时，在 draft 中描述拟替代的前任，但暂不使其失效。只有继任者已实现、被接受使用并验证后，才写互相指向的 `supersedes` 与 `superseded_by`，并把前任标为 `superseded`。

英文使用 [assets/spec-template.md](assets/spec-template.md)，中文使用 [assets/spec-template.zh_CN.md](assets/spec-template.zh_CN.md)。合并对本设计无帮助的模板分区；已有 Spec 不必为匹配新模板而重排。

## 完成

回读修改后的设计，检查矛盾、缺失的后果和没有依据的完成声明；CLI 可用时运行 `hello-scholar docs check`。返回当前选择、具体改动、修订与状态、关键证据，以及仍阻碍推进的决定。
