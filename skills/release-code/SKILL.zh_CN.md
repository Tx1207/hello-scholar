# Release Code

公开版本让别人能复现论文结果、看懂方法，同时看不到内部路径、密钥、废弃实验或开发历史。开发仓库始终是唯一的权威来源：公开版本从它重新生成，从不并行开发。

## 确定发布要支撑什么

从发布要支撑的结论出发：论文中报告的结果，或用户选定的部分 Run。发布要复现的是这些结论，而不是项目里的每一份 Run Record。每条结论记录报告值、复现结果在多大容差内算成功，以及产生它的 Run（如果有）；Run 提供确切的条件，例如配置、checkpoint 和数据。用 `manage-specs` 把范围保存为 `type` 为 `capability` 的发布 Spec：每条结论一个 `AC-NN`，写明报告值、容差和 Run ID，以及包含的代码路径、明确排除的内容、许可证、第三方代码及其许可证、公开仓库。找不到产生条件的结论如实报告，不凭信任发布。

## 追踪最小代码路径

从每个 Run 的 `entry` 和实际生效的配置出发，沿 import 和配置引用找到真正执行的代码，只带走这条路径。快速迭代的研究代码里常有只差几个常量的多份脚本；发布时只保留一个带参数的入口，变体用配置表达。需要时为可读性重写，但不改变计算。废弃实验、集群启动封装和调试开关一律不带。

## 在隔离分支上组装

公开仓库绝不能收到开发历史。默认新建名为 `release` 的 orphan 分支，在开发目录之外的独立 worktree 中检出，例如 `../<repo>-release`；把公开仓库添加为名为 `public` 的 remote，并让推送只映射这个分支：

```bash
git config remote.public.push refs/heads/release:refs/heads/main
```

用户选择了其他方式时，按发布 Spec 执行。

让发布对读者完整：依赖说明、所发布结论的训练和评测代码、预训练权重或获取方式、带结果表且每行附精确命令的 README，以及 LICENSE 和第三方声明。README 从 [assets/readme-template.zh_CN.md](assets/readme-template.zh_CN.md) 开始写，删掉不适用的部分；公开 README 的语言按发布 Spec，默认英文时用 [assets/readme-template.md](assets/readme-template.md)。内部绝对路径、主机名和集群设置替换为有文档说明的默认值或参数。完整性与泄漏检查读取 [references/release-checks.zh_CN.md](references/release-checks.zh_CN.md)。

## 检查泄漏

提交前，在组装好的目录中搜索密钥和 token、内部主机名和绝对路径、私有或未授权的数据、个人信息，以及不应公开的内部注释。有 gitleaks 这类密钥扫描工具时使用它，没有时如实说明。任何发现都要修复后才能提交。

## 验证复现

在全新 clone 和全新环境中，用记录的 checkpoint、数据和配置运行 README 中的命令，把每个结果与论文中的报告值、或选定的 Run Record，在 Spec 规定的容差内比较。把每项比较作为证据写到对应的 `AC-NN`。某条结论无法复现时，报告差距和原因；不删掉这条结论，也不放宽容差。通常先用发布的权重做评测，这项比较是发布 Spec 中的验收证据。完整重新训练成本高，需要单独授权，并通过 `record-experiment` 新建 Run，`derived_from` 指向原 Run。服务器无法联网时，在能联网的机器上验证安装步骤，或把环境打包供离线使用，例如用 conda-pack，并说明实际做了哪种验证。

## 提交并停下

把发布作为一个快照提交。提交说明按项目的提交说明规则书写，例如 `chore(release): export Table 2 claims from 69f0ed0`，并在正文写明来源的开发提交、所复现的结论及其 Run ID，以及发布 Spec 的修订号。然后停下，报告已复现和未复现的结论、泄漏检查结果和推送命令。推送、把仓库设为公开或上传权重，都需要用户明确授权。

## 保持同步

只有开发代码的改动影响到已发布结论时才重新导出，并对这些结论重新做复现检查。外部 pull request 先移植到开发仓库，再重新导出；不能只合并到发布分支上。
