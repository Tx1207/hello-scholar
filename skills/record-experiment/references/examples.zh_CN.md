# record-experiment 示例

这些案例覆盖仅凭 SKILL 正文仍难以判断的情形。

## 1. 启动前先复用

用户要求评估 λ72 模型第 8000 步。`runs/INDEX.md` 显示 `20261010-0900-l72-dists-s6000` 使用 `entry: scripts/eval_uvg96.py` 和相同评测集。用 `--step 8000` 重跑该入口，作为新 Run，设 `derived_from: 20261010-0900-l72-dists-s6000`，并在 Record 中说明只有 checkpoint 步数不同。不要复制脚本去改常量。如果相同评测条件下第 8000 步的结果已经存在，直接从其 Record 报告，不再运行。

如果此前 Run 使用了不同的评测脚本或数据划分，只补跑有差异的部分，并说明旧结果为何不可比。

## 2. 相似执行，不同证据价值

在远程 GPU 上跑 20 条样本，检查配置解析并走到推理。之后没有决定依赖其输出：报告可执行性，不建 Record。另一次 20 条样本在固定诊断集上比较两种预处理，以决定下一步研究哪一种：需要保留，并说明诊断集只支持这个窄选择，不代表整体模型质量。两种情况都不由成本和样本数决定。

## 3. 启动准备与正式重试

已约定的 A/B 比较值得记录。A/B 启动前，三次启动检查分别因调度设置、DDP rank 错误和进程组冲突失败。保留一份 planned Record，时间戳为 null，追加每次错误与修复，各次检查日志分开保存。检查通过后，从正式实验的真实开始时间继续同一份 Record。

如果 A/B 本身已经启动后失败，以 `failed` 关闭该 Run。获授权的重试另建 Run，`derived_from` 指向失败的那次；条件允许时复用启动计划，并从已完成的阶段继续，例如已编码的数据或已保存的 checkpoint。

## 4. 负结果与故障

一次有效、可比的评测得到 81.2，基线为 82.0：`status: completed`；只有主 Agent 真正作出决定时才写 `decision: do-not-adopt`。验证阶段 CUDA OOM，没有产生指标：`status: failed`，记录错误、尝试的配置、日志和退出码。OOM 说明该配置的资源限制，并未检验方法本身。

## 5. 对已有 Run 的只读查询

对于“看看最新 loss”或“tmux 还活着吗”，读取已有证据并回答。新发现的完成或错误要报告；只有任务已经包含维护该 Run 或用户要求时，才追加到 Record。
