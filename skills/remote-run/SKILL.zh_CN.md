# Remote Run

AI 工具留在本地机器上，服务器只负责执行代码。代码通过 SSH 用 Git 单向部署，命令通过 SSH 运行，输出、Traceback 和退出码原路返回，AI 可以直接修复后重跑，用户不需要复制粘贴。长任务在服务器的 tmux 中运行，SSH 断开或工具超时都不会杀掉它。

## 先确认事实

无法自行查明的要问用户：SSH 别名、服务器上的项目路径、conda 的 `bin/activate` 路径和环境名，以及数据、checkpoint 和输出放在哪里。能查明的自己检查：用 `ssh -o BatchMode=yes <别名> hostname` 确认免密登录，确认服务器上有 Git、`tmux` 和 `rsync`、服务器 bash 版本不低于 4.4，以及本地项目是 Git 仓库。本地项目是代码的权威来源，不在服务器上修改代码。

不要自行修改 `~/.ssh/config`、在服务器上安装软件或改服务器设置。登录需要密钥或连接复用时，把要添加的配置块给用户，包括 `ControlMaster auto`、`ControlPersist` 和 `ServerAliveInterval`。服务器断网是出于规定时，不提议反向隧道；原因不明时，先问清再考虑。

## 安装脚本

把 `assets/scripts/remote/` 中的文件复制到项目的 `scripts/remote/`，保持 `.sh` 文件可执行，提交它们，并填好 [remote.env](assets/scripts/remote/remote.env)。填写前先只读盘点两边：列出服务器上的顶层条目及其大小，以及本地的顶层条目，包括被 Git 忽略的目录和体积大的目录。推荐 `REMOTE_SERVER_DIRS`：存放服务器数据和输出的目录，通常是 `data artifacts tmp`，加上 `outputs/`、`checkpoints/`、`wandb/` 等旧输出目录；推荐 `REMOTE_LOCAL_EXCLUDES`：必须只留在本地的目录，例如 `.venv/`、`node_modules/`。把推荐整理成表格请用户确认；以 Architecture 中记录的布局为准。数据、权重和输出不纳入 Git 跟踪。

服务器上的 `REMOTE_DIR` 会成为一个 Git 工作区。每次同步把一个提交推送到 `refs/remote-run/deploy` 并在服务器上检出：本地工作区干净时用 `HEAD`，否则用工作区内容生成一个临时提交，它从不改动本地分支或暂存区。Git 只修改被跟踪的文件，所以服务器上未跟踪的数据、权重、日志和输出永远不会被修改或删除；本地删除或改名的代码，服务器上也会相应删除或改名。临时提交不包含 `REMOTE_SERVER_DIRS`、`REMOTE_LOCAL_EXCLUDES` 以及匹配 `REMOTE_PROTECTED_PATTERNS` 的文件（默认是 `*.pt`、`*.safetensors` 等权重格式）。服务器上被修改的跟踪文件，或位于提交新增路径上的未跟踪文件，只要与要部署的内容不同，同步就停下、不改动服务器代码；已经与部署内容一致的服务器改动和未跟踪文件（例如复制式同步留下的状态，或拉回本地后提交的结果）会被接受。从 rsync 版 remote-run 升级时，服务器上旧的 `scripts/remote/` 文件与新版本不同：经用户确认后，用 `delete.sh` 删除它们再同步。子模块的内容不会部署，项目有子模块时同步会提示。

第一次部署到一个非空、且还不是 Git 工作区的目录（接入已有项目时的常见情况）时，只做预演：统计已经一致的文件，列出内容不同、将被覆盖的文件，然后以退出码 3 结束，不创建任何东西。把预演结果给用户看，用户同意后才加 `--confirm-first-sync`；被覆盖的服务器文件会先备份到 `tmp/remote-run-backup/`。

| 脚本 | 用途 |
| --- | --- |
| `sync.sh` | 用 Git 部署本地提交或工作区内容，并输出部署的提交；`--dry-run` 预览改动；第一次部署到非空、非 Git 的目录需要 `--confirm-first-sync`。 |
| `run.sh` | 先同步，再在前台运行，或用 `--bg --name NAME` 在 tmux 中运行；拒绝删除和移动命令；`--run RUN_ID` 把正式 Run 唯一一次正式执行的日志写到 `runs/<run-id>/logs/`；`--run RUN_ID --startup` 把可反复运行的启动检查记在同一目录，编号为 `startup-NN`。 |
| `logs.sh` | 任务状态、带部署提交和退出行的任务日志、最近的 stdout 和 stderr、GPU 使用情况。 |
| `stop.sh` | 停止后台任务，并在任务日志中记一笔。 |
| `pull.sh` | 把 `runs/<run-id>/results/` 拉回本地，供 Record 引用数值。 |
| `delete.sh` | 删除明确指定的、服务器上未跟踪的残留文件，删除目录需加 `--recursive`；拒绝通配符、项目外的路径、受保护的目录、权重文件、含有权重文件的目录，以及已部署代码跟踪的路径。 |

任务在部署后的工作区中运行，每份任务日志都记录部署的提交：正式执行是真实提交（`run.sh` 只从已提交的本地代码启动正式执行），启动检查和普通任务在未提交代码上运行时是临时提交。运行中的任务不受之后同步的隔离，所以不要修改它还会读取的文件，例如配置或它结束时调用的评测脚本。stdout 和 stderr 分别写入文件，符合 record-experiment 的要求；正式 Run 的正式执行只能启动一次；在此之前的启动检查按编号保存、可反复运行，与 record-experiment 中 planned Record 的规定一致。tmux 名称按精确匹配，名为 `train` 的任务不会和 `train-long` 冲突。

## 写入项目规则

把 [assets/remote-rules.md](assets/remote-rules.md) 或 [assets/remote-rules.zh_CN.md](assets/remote-rules.zh_CN.md) 追加到项目的 AGENTS.md 和 CLAUDE.md 中、hello-scholar 管理块之外，并填入真实的别名。AI 运行的每条命令都依赖这些规则，所以它们必须每轮都加载；日常运行时本 skill 并不会被加载。

用户希望把 AI 的命令限制在这些脚本内时，建议在其工具中加权限规则；未经同意不要修改工具设置。

## 在真实服务器上验证

使用几秒内就能结束的命令，逐项报告实际结果：

1. 免密登录能返回主机名，不出现提示。
2. 对已有目录，第一次部署只预演、不做任何修改；确认后，内容不同的服务器文件被备份，服务器独有的文件保留。之后本地删除或改名的文件，服务器上也相应删除或改名，数据、权重和其他未跟踪文件不受影响。
3. 未提交的改动以临时提交部署，本地分支、暂存区和状态保持不变；只留在本地的目录和权重文件不会部署。
4. 服务器上有被修改的跟踪文件，或有内容不同的未跟踪文件时，同步停下、不改动服务器代码。
5. 前台 GPU 检查输出 `True`、退出码为 0；运行一个会报错的脚本，本地能看到完整 Traceback，退出码非 0。
6. 后台任务立即返回，SSH 命令结束后仍在运行，`logs.sh` 能看到进度和最后的 `[exit 0 ...]`；同名的第二个任务被拒绝，`stop.sh` 能停止运行中的任务。
7. 本地有未提交改动时，正式执行被拒绝；提交后可以启动，任务日志记录该提交。启动检查依次记为 `startup-01`、`startup-02`，同一 Run 的第二次正式执行和之后的启动检查都会被拒绝。
8. `delete.sh` 能删除指定的未跟踪残留文件，并拒绝 `data/` 或 `runs/` 下的路径、权重文件、含有权重文件的目录以及被跟踪的代码；`run.sh rm ...` 会被拒绝。

验收后删除测试文件和 tmux 会话。检查失败时报告输出和可能的修复办法；不要为了让检查通过而修改服务器。
