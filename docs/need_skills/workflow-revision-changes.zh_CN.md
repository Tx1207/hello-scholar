# Skill 集合重组：中文修改对比

日期：2026-10-12。对应 [SPEC-001 Revision 4](../../hello-scholar/specs/agent-workflow/SPEC-001-research-development/spec.md)，改造前基线为本地提交 `5e950df5b3b3209a5b262e24b21800df63ffcaaa`。本文随本次实现保存，解释实际差异及本次验证；唯一当前进度继续由[项目总览](spec-driven-skill-design.md)维护。

**这次已经修改主 AGENTS、八个独立 Skill、中英文模板、参考资料和安装升级。** 共同目标是让 Agent 作出有依据的选择，并让读者从交付物直接理解具体变化与理由。方法论写进判断过程，必要格式用于保存和交换结果。

## 1. 集合如何变化

| 原入口 | 当前处理 | 现在主要解决什么问题 |
| --- | --- | --- |
| `grilling` | 保留独立能力并改写方法 | 区分事实与用户选择，沿决定依赖追问会改变方案的未知；答案不再影响选择时停止。无需项目或 Spec。 |
| `manage-specs` | 保留并加深方法 | 找到设计的已有归属，把决定、依据、具体后果与验收标准连接起来；有未决问题也能先保存 Draft。 |
| `record-experiment` | 保留单次运行职责，收紧保留门槛 | 重建实际生效的运行条件，区分执行状态、比较有效性和单次结论；不承担整个科研项目的设计与调度。 |
| `converge-to-spec` | 扩展、更名为 `review` | 从契约和关键假设寻找有证据的反例；能独立审查方案、代码或研究证据，没有 Spec 也可用。 |
| 无独立入口 | 新增 `ponytail` | 沿调用关系追查机制保护的真实需求，在指定范围实际简化代码，验证应保留的行为。 |
| 无独立入口 | 新增 `synthesize` | 选择值得回答的问题，连接证据、认识变化与下一步，按用途提炼有条件的可复用经验。 |
| `docs-maintenance` | 保留并加深方法 | 区分源事实、当前解释与生成导航；沿真实变更修正矛盾，只把已核实、已采用的结构写成现状。 |
| `handoff` | 保留并加深方法 | 从接手者下一步行动倒推信息缺口，只补保存现有文件、代码和 Git 无法恢复的内容。 |
| `takeoff` | 移除 | 目标重判和假设辨认进入主 Agent 的共同思考方法。 |
| `landing` | 移除 | 资源、约束和停止判断进入主规则；主动代码精简由 ponytail 负责。 |
| `crash-audit` | 移除 | 反例、影响和证据缺口由 review 负责。 |

当前默认安装八个 Skill。它们按任务选择，可以直接使用；主 Agent 负责方案、实施、验证和结果整合，不新增强制 `implement` 入口或固定调用顺序。

## 2. 主 AGENTS 的实际修改

| 关注点 | 改造前 | 修改后及目的 |
| --- | --- | --- |
| 工程目标 | “编写无需推倒重来的代码”容易被理解为预防所有未来变化 | 完成当前目标所需的最小完整改动，保留可信证据与可接续事实。是否保留复杂机制由当前用途决定。 |
| 五个方法 | 已列出方法，但与任务职责和具体产物的关系仍不充分 | 按当前问题选用，并要求产生可以判断的结果；各 Skill 深入自身领域，不复制五遍完整方法清单。 |
| Spec 保存 | 独立质询和纯讨论的边界明确，持续研发中的保存衔接不足 | 持续研发形成可审阅方案后，主 Agent 自动保存到已有归属或创建 Draft；关键未知也一起保存。 |
| Spec 修订 | 小改动无需新建 Spec，容易被误读为不用维护文档 | 新建与更新分别判断；已有范围、接口、行为或验收受影响时，本轮结束前更新。证据补充不虚增 Revision。 |
| 状态查询 | “查询任务状态或结果，先查 Run Record”范围过宽 | 设计查 Spec，科研运行查 Record，普通开发查任务入口、代码、Git 与验证证据。 |
| 方案表达 | 容易只说准备做什么 | 概要交代改动对象、具体改法、必要步骤、关键取舍和验证办法；先让读者理解，再压缩重复。 |
| 连续工作 | 专项入口之间容易漏接维护责任 | 主 Agent 整合获授权的决定、证据和审查处理；独立 Skill 不成为固定阶段，也不各自产生竞争事实源。 |

例如，批量评分方案的概要可以直接说明：在 `scorekit.py` 增加 `score_batch(items)`，返回保序列表；空 `values` 只产生该项错误，其余项继续评分；非空项复用原函数。实施依次补兼容与批量用例、增加包装函数、更新调用示例；验证原接口、逐项错误、顺序和类型。读者由此知道具体做法，也能判断取舍。

### 五个方法怎样进入实际工作

| 方法 | 适用问题与结果 |
| --- | --- |
| 第一性原理 | 目标或方向可能有误时，分开真实需要、已知事实与继承假设，重新推导选择。需要用户决定的部分可交给 grilling。 |
| 对抗性审查 | 关键假设尚有疑点时，寻找成立条件、反例与实际后果；无实质问题时允许返回没有发现。 |
| 消融实验 | 不清楚收益来源时，用可比条件检验机制贡献；存在相互作用时允许多条件设计。 |
| 奥卡姆剃刀 | 机制越来越多时，问删除它会损害哪个真实目标或契约；没有当前必要性的部分可以简化。 |
| 高内聚、低耦合 | 明确行为、决定、状态与文件的归属；经常一起使用的能力仍可独立存在。 |

## 3. 科研增量、Spec 与 Run

**一个科研增量减少一个会影响下一步选择的不确定性，可以包含多次 Run。** 主 Agent 在 Spec 中明确问题、对照、评价口径、重复安排、预算、解释规则和停止条件；运行者保存约定的单次事实。

研究完成、执行成功、比较有效、方法获采用分别判断。有效负结果可以完成“检验是否有收益”的任务；若采用还要求效果和成本达到阈值，这些条件需要自己的证据。OOM 可以说明当前资源配置不可行，不能据此宣布算法假设失败。

| 实际活动 | 当前保留方式 |
| --- | --- |
| 快速但会改变研究选择的正式比较 | 保留 Run，速度快不降低证据价值。 |
| 普通 import、连接、启动 smoke、重复轮询 | 在本轮验证或已有日志中说明，不单独创建科研 Run。 |
| 昂贵、远程、GPU 准备或失败 | 看复现、恢复、资源边界或决策价值；成本和临时产物本身不充分。 |
| 已有 Run 出现新状态或结果 | 更新同一 Record，不因轮询生成新身份。 |
| 汇总研究笔记、撰写周报 | 引用已有材料；生成文字不创建 Run。 |
| 新派生计算产生有保留价值的证据 | 为实际计算保留 Run，并关联输入来源。 |

Spec 模板把当前决定、具体设计及判断标准连起来；Run 模板从原来的 12 段收拢为 5 组信息：当前发现与解释、问题与比较、执行信息、产物位置、重要执行事件。运行前如实标记尚无结果，之后把关键结果和解释放在前面，复现所需的实际命令、环境、时间和原始输出仍保留。

本轮修改新任务的默认行为，历史 Run 的原始条件与结论保持原文。Spec schema 1、新 Record schema 2 和历史 Record 的读取兼容没有改变。

## 4. synthesize 怎样降低理解负担

它的核心工作包括选择读者真正需要理解的问题，辨认材料相互支持、冲突或不可比较的关系，解释新证据怎样改变判断，并从中提炼能帮助后续选择的方法。经验需要说明适用条件和调整依据；材料只有进度时就准确总结进度，不制造洞察。

同一材料可以形成不同深度的产物：研究笔记保留推理、反例和认识演变，周报只展开读者判断进展与后续安排所需的部分。两者事实含义保持一致。主 Agent 的普通回答直接遵循共同表达要求，不必每次调用 synthesize。

本次构造材料试用中的关键认识是：早期的“提升 2 个百分点”使用了不同测试集和种子，不能归因于候选方法；统一条件后的三组配对差值为 +0.4、−0.4、0.0 个百分点，平均收益为零，训练时间增加 8%–9%。因此采用收益尚未获得支持，不能只选最好的一次。

可保留的方法是：**复用历史基线前，先核对它是否能回答当前比较问题；解释配对结果时保留正向、负向和持平证据，并区分效果、成本和执行状态。** 它能改变下一次实验的做法，同时没有把一个案例提升为“该方法普遍无效”。这段使用演练用构造数据，不是实际科研成果。

主审也观察到研究笔记在结论、后续安排和经验中重复了一些判断，因而细化了共同写作方法：每段推进一个必要的事实、关系或影响；后文承接已解释的证据；合并重叠经验。没有增加固定字数、标题或“每次必须总结方法论”的要求。这次文字细化只做了一致性核对，没有追加模型案例证明其效果。

## 5. 独立审查与安装升级

`review` 默认只读，交付有实质影响的发现、触发条件、后果、依据及最小处理办法；用户要求“检查并修复”时，主 Agent 继续完成授权范围内的修复。`ponytail` 则在清理请求下直接修改指定范围，两者保持各自用途。

需要另一模型审查时，交出明确的对象、Spec Revision 或代码工作树范围、实际证据状态、读取边界和唯一输出位置。没有可用的指定客户端时，生成可移交的请求，并明确该模型尚未执行。相关代码、数据或 Run 变化后，旧审查只覆盖原状态，即使 Spec Revision 没变，也要按影响说明需复查的判断。

安装器沿用现有机制，退休清单新增 `converge-to-spec`、`takeoff`、`landing`、`crash-audit`。清理已确认归属且未修改的旧安装，用户修改、未知来源和其他来源链接继续受到保护；项目 Spec、Run 和历史材料不因升级而被删除。安装命令、数据 schema 与版本号没有额外变化。

### 三个独立构造任务

三份小项目通过真实 CLI 以 copy 模式安装全部八个 Skill 和根规则，再交给不继承主会话的新子 Agent。每项只运行一次，未提供期望答案，没有旧版或无 Skill 对照，也没有调用原生 Claude。主 Agent 读回实际产物；独立审查者另行检查材料与结果的一致性。

| 构造任务 | 请求与条件 | 实际产物及核对结果 |
| --- | --- | --- |
| 批量评分设计 | 现有 `score_values(values)`；要求保序、逐项空值错误、原接口兼容、标准库；只设计，未点名 Spec | 自动创建 Draft Revision 1。给出 `score_batch(items)`、具体结果格式、错误隔离、实施步骤和 AC；代码不变，未创建 Plan/Tasks 或 Run。 |
| 预处理代码清理 | 7 个类只承担内部转发；公开 summarize 支持 baseline 与 clipped，两种模式有研究语义差异 | 只修改 metrics.py，收拢为直接函数；保留负值处理差异、字段、错误消息和先后顺序。原 5 项行为测试修改前后通过，主 Agent 再次执行也通过。 |
| 研究笔记与周报 | 4 份构造笔记，含不可比早期结果、三组配对证据、工程进度和预算；要求整理，不启动实验 | 生成两份正文；原材料不变；完整保留差值、时间成本与限制，区分当前建议和已采用决定；不创建 Run，也未发送飞书。 |
