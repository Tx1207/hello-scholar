01

Skill 按具体问题分工

八个能力可以独立调用。通用设计与实施由主 Agent 承担，按任务需要选择 Skill，没有固定调用顺序。

grilling保留 · 改写

澄清会改变选择的未知

先查可查事实，再沿决定之间的依赖追问。剩余答案不再影响方案或验收时停止，不要求穷尽所有分支。

交付明确选择、理由与关键未决项；独立使用无需项目或 Spec。

manage-specs保留 · 深化

把设计和验收依据连起来

先找到设计的已有归属，再连接决定、具体改法、取舍和验收标准。有未决问题也可以先保存 Draft。

维护 Spec；范围或判断标准变化时修订，补证据不虚增 Revision。

record-experiment保留 · 收紧边界

按证据价值保留一次运行

记录实际生效条件与单次解释，区分执行状态、比较有效性和采用结论。是否记录取决于研究、复现、恢复或决策价值。

维护 Run Record；普通连接检查、启动 smoke 和轮询通常不新建 Run。

review扩展 · 更名

从验收对照扩展到独立审查

承接 converge-to-spec，可检查方案、代码、实现与研究证据。Draft 和部分实现也可审查，没有 Spec 同样可用。

默认只读；返回问题、触发条件、证据、后果和最小处理方向。

ponytail新增

实际清理非必要复杂性

沿调用关系确认机制保护什么真实需求，在指定范围删除或合并多余结构，保留公共契约和有科学用途的控制条件。

清理请求下实施并验证；仅要求评估时保持只读。

synthesize新增

让材料形成可理解的判断

围绕读者的问题组织思路、实验结果、研究笔记或周报。解释证据关系与认识变化，保留能指导后续选择的有条件经验。

交付可直接使用的正文；汇总已有材料本身不产生新的 Run。

docs-maintenance保留 · 深化

按事实归属维护文档

区分源事实、当前解释与生成导航。Architecture 只写已核实、已采用的结构；Index 用于定位，不替代来源。

按授权检查、同步或修复文档；docs check 只读，docs sync 写入生成索引。

handoff保留 · 深化

只补接手者缺少的上下文

从下一步行动倒推信息缺口，补充尚未解决的选择、在运行任务或具体阻塞；已有文件与 Git 能恢复的内容直接引用。

保存可接续的 Handoff，不复制整段聊天或另一份设计文档。

退出的入口，职责去了哪里？

converge-to-spec→review：保留验收对照，扩大审查对象。
takeoff→主 Agent：目标重判与假设辨认。
landing→主规则：资源、约束与停止判断；代码精简归 ponytail。
crash-audit→review：反例、实际影响与证据缺口。
02

主规则承担连续工作的责任

共同规则明确谁推进任务、何时保存设计、如何查状态，减少专项能力之间的责任遗漏。

主 Agent 的责任：围绕当前目标形成方案，完成已授权实施与验证，整合审查发现和运行证据，并把受影响的项目事实更新回原归属。

工程目标更加具体

原来强调“编写无需推倒重来的代码”，容易引向对未来变化的过度预防。

现在：完成当前目标所需的最小完整改动，保留可信证据与可接续事实；复杂性由实际需求和契约支撑。

设计形成后及时保存

原来对纯讨论边界较清楚，但持续研发中的保存衔接不足。

现在：形成可审阅方案后，保存到已有归属或创建 Draft，连同关键未知一起保存。独立质询、临时解释和明确不保存的请求仍可在对话完成。

小改动也判断是否影响已有设计

“小改动无需新建 Spec”容易被误解为无需维护任何设计文档。

现在：分别判断新建和更新。已有范围、行为、接口、约束或验收受影响时，本轮更新对应设计。

按问题查正确的事实源

原来“查任务状态先查 Run Record”的范围过宽。

现在：设计进度查 Spec，科研运行查 Record，系统结构查 Architecture；普通开发查任务入口、代码、Git 和验证证据。

五个思考方法怎样落实到工作中
第一性原理
方向可能有误时，区分真实目标、已知事实与继承假设，重新推导选择。
对抗性审查
核心假设有疑点时，寻找具体反例、触发条件与实际后果。
消融实验
机制贡献不清时，设计可比条件；存在相互作用时允许多条件比较。
奥卡姆剃刀
机制增加时，判断删除它会损害哪个当前目标或真实契约。
高内聚、低耦合
明确行为、状态、决定与文件的负责人，让依赖符合职责。
03

总体设计与单次执行各有归属

一个科研增量围绕会影响下一步选择的不确定性展开，可以包含多次 Run。主 Agent 负责总体问题与跨 Run 判断，运行者保留实际执行事实。

Spec：决定做什么、怎样判断

  • 连接当前选择、具体设计、必要实施步骤和验收标准。
  • 科研比较交代对照、数据与评价条件、重复策略、预算和停止条件。
  • 保留稳定的 AC-NN，在旁边记录有效证据与缺口。
  • 范围或判断标准变化才递增 Revision；补证据或变更生命周期不递增。
hello-scholar/specs/<topic>/SPEC-NNN-<name>/spec.md

Run Record：实际运行了什么

  • 保留影响研究判断、复现、恢复或资源决策的执行，即使很小或结果为负。
  • 普通 import、连接、配置、启动 smoke 与重复轮询通常留在任务验证中。
  • 已有 Run 的新事实更新同一 Record，不因轮询建立新身份。
  • 模板由 12 段收拢成 5 组信息：发现与解释、问题与比较、执行信息、产物位置、重要事件。
runs/<run-id>/record.md

执行完成、比较有效、研究问题得到回答、满足采用条件分别判断。例如，OOM 说明资源限制；有效负结果可以完成调查，但不一定支持采用方法。

Spec schema 1、新 Record schema 2 及历史读取兼容保持不变。过去 Run 的实际条件和原结论继续保留。

04

审查有明确边界，交付解释判断依据

审查者提供独立发现，主 Agent 负责核对和处理。共同表达规则让读者从交付物理解变化、证据与后果。

审查从设计阶段就可开始

方案、代码、部分实现和研究证据都可审查。默认保持被审查材料不变；要求“审查并修复”时，先确认发现，再继续授权内的修复与验证。

指定另一模型但客户端不可用时，交付可转交的审查请求，并明确该模型尚未执行。

正文说明结果与关键理由

方案交代改哪里、怎样改、必要步骤、取舍和验证办法；结果说明实际变化、本次证据及剩余问题。链接供追溯，关键解释留在正文。

按理解需要选择文字、表格、图示或交互；避免在多个章节重复同一判断，也不强制每次产出方法论总结。

确定本轮审查对象

交代 Spec Revision、代码范围、输入与 Run 状态，让审查者检查稳定的材料。

返回发现，按需保存

默认在对话返回。保存属于任务范围时，Spec 审查写入同目录 review.md，按轮次保留对象、发现和覆盖范围。

主 Agent 处理并整合

记录采用、不采用及理由或待核实事实。输入变化后，复查受影响判断；旧审查仍只覆盖原状态。
